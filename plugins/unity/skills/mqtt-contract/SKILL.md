# Sollertia Unity MQTT contract

Documents the MQTT contract between `sollertia-unity-tasks` and `sollertia-experiment`. Each topic is owned by a
specific C# script inside the Unity project; this skill is the single source of truth for topic names, payload
shapes, and direction.

---

## Scope

**Covers:**
- Every MQTT topic published or subscribed to by `sollertia-unity-tasks` scripts
- Payload shapes (trigger-only vs JSON-serialized typed messages)
- Owning script and initialization site for each channel
- Required topic conventions (trailing slash, paired `*Trigger/` topics)
- Diagnostic checklist when a message is sent from one side but not received on the other

**Does not cover:**
- The `MQTTChannel` and `MQTTChannel<T>` class APIs (see `/gimbl-framework`)
- MQTT broker installation or configuration (see the project `README.md`)
- `sollertia-experiment`'s publishing side (owned by sollertia-experiment skills)
- Topic changes to external downstream consumers (MQTTnet, dashboards, etc.)

---

## Topic conventions

- Every topic ends with a trailing slash (`"LickPort/"`, not `"LickPort"`). Omitting the slash silently creates a
  different subscription.
- "Trigger" topics come in pairs: `<Name>Trigger/` is a listener that asks Unity to publish on `<Name>/`. The former
  carries no payload; the latter carries a JSON-serialized message.
- Topic strings are **literals** in the C# source — there is no central registry. Grepping for `MQTTChannel(` is the
  only reliable way to enumerate them. This skill keeps the enumeration synchronized manually.
- `MQTTChannel` (untyped) sends/receives empty-payload trigger messages. `MQTTChannel<T>` sends/receives
  `Encoding.UTF8.GetBytes(JsonUtility.ToJson(message))` — a JSON payload whose deserialization target is `T`.

## Topic catalog

### Task lifecycle (owned by `Task.cs`)

| Topic                  | Direction            | Channel type                       | Purpose                                                         |
|------------------------|----------------------|------------------------------------|-----------------------------------------------------------------|
| `CueSequenceTrigger/`  | Listener (Unity ← experiment) | `MQTTChannel`             | Experiment asks Unity to publish the full cue byte array        |
| `CueSequence/`         | Publisher (Unity → experiment) | `MQTTChannel<SequenceMessage>` | Unity sends the pre-generated byte array of cue codes    |
| `SceneNameTrigger/`    | Listener (Unity ← experiment) | `MQTTChannel`             | Experiment asks Unity for the active scene name                 |
| `SceneName/`           | Publisher (Unity → experiment) | `MQTTChannel<SceneNameMessage>` | Unity sends the string name of the active scene         |
| `RequireLick/True/`    | Listener (Unity ← experiment) | `MQTTChannel`             | Experiment disables lick guidance mode (`requireLick = true`)   |
| `RequireLick/False/`   | Listener (Unity ← experiment) | `MQTTChannel`             | Experiment enables lick guidance mode (`requireLick = false`)   |
| `RequireWait/True/`    | Listener (Unity ← experiment) | `MQTTChannel`             | Experiment disables occupancy guidance (`requireWait = true`)   |
| `RequireWait/False/`   | Listener (Unity ← experiment) | `MQTTChannel`             | Experiment enables occupancy guidance (`requireWait = false`)   |

Payload shapes for the publishers:

```csharp
// CueSequence/
public class SequenceMessage
{
    public byte[] cueSequence;   // flattened cue codes for the full random maze
}

// SceneName/
public class SceneNameMessage
{
    public string name;          // SceneManager.GetActiveScene().name
}
```

### Stimulus delivery (owned by `StimulusTriggerZone.cs`)

| Topic              | Direction                    | Channel type    | Purpose                                                    |
|--------------------|------------------------------|-----------------|------------------------------------------------------------|
| `Gimbl/Stimulus/`  | Publisher (Unity → experiment) | `MQTTChannel` | Fires when a stimulus trigger zone activates               |
| `LickPort/`        | Listener (Unity ← experiment)  | `MQTTChannel` | Hardware lick detection from the sollertia-experiment side |

Behavior notes:
- `Gimbl/Stimulus/` is **fire and forget** — no payload, no ack. Sent once when
  `StimulusTriggerZone.TriggerStimulus()` decides the conditions are met.
- `LickPort/` is **also received by** `LickStimulusSpawner.cs` (UI) and `SimulatedLinearTreadmill.cs` (debug
  simulation) — see "Multi-consumer topics" below.

### Occupancy movement guidance (owned by `OccupancyGuidanceZone.cs`)

| Topic                 | Direction                    | Channel type                       | Purpose                                       |
|-----------------------|------------------------------|------------------------------------|-----------------------------------------------|
| `Gimbl/TriggerDelay/` | Publisher (Unity → experiment) | `MQTTChannel<TriggerDelayMessage>` | Sends brake-activation delay for occupancy failures |

Payload:

```csharp
public class TriggerDelayMessage
{
    public int delayMs;          // milliseconds the treadmill should block movement
}
```

Published only when occupancy guidance mode is active (`requireWait == false`) and the animal fails the occupancy
requirement. Consumed by sollertia-experiment to brake the treadmill for the specified duration.

### UI feedback (owned by `LickStimulusSpawner.cs`)

| Topic             | Direction                   | Channel type    | Purpose                                               |
|-------------------|-----------------------------|-----------------|-------------------------------------------------------|
| `LickPort/`       | Listener (Unity ← experiment) | `MQTTChannel` | Spawns a lick indicator on the experimenter's UI canvas |
| `Gimbl/Stimulus/` | Listener (Unity ← Unity)      | `MQTTChannel` | Spawns a stimulus indicator on the experimenter's UI canvas |

Both subscriptions are passive — `LickStimulusSpawner` never publishes. The `Gimbl/Stimulus/` case is **intra-Unity**:
`StimulusTriggerZone` publishes, `LickStimulusSpawner` and sollertia-experiment both subscribe.

### Simulation (owned by `SimulatedLinearTreadmill.cs`)

| Topic        | Direction                     | Channel type    | Purpose                                            |
|--------------|-------------------------------|-----------------|----------------------------------------------------|
| `LickPort/`  | Publisher (Unity → everyone)  | `MQTTChannel`   | Simulates a hardware lick when the user left-clicks |

This publisher is **development-only**. In production, `LickPort/` is published by `sollertia-experiment` from
hardware input. The `SimulatedLinearTreadmill` component only exists in scenes configured for manual testing.

## Multi-consumer topics

Two topics have more than one subscriber inside Unity. When editing either topic, verify every listener still
behaves correctly:

### `LickPort/`

Subscribers inside Unity:
- `StimulusTriggerZone.cs` — records whether a lick occurred while the animal was in the zone.
- `LickStimulusSpawner.cs` — spawns a UI indicator.

Publisher:
- `SimulatedLinearTreadmill.cs` (dev only) — on left click.

External:
- `sollertia-experiment` publishes from hardware lick port; consumes from nothing.

### `Gimbl/Stimulus/`

Subscribers inside Unity:
- `LickStimulusSpawner.cs` — spawns a UI indicator.

Publisher:
- `StimulusTriggerZone.cs` — fires once per armed zone entry.

External:
- `sollertia-experiment` subscribes to log the stimulus event against the session timeline.

## Lifecycle rules

All channels are created in `Start()` (runtime, not editor) and removed in `OnDestroy()`. If you add a new channel,
follow the pattern already established in `Task.cs`:

```csharp
// Start()
_myListener = new MQTTChannel("MyTopic/", isListener: true);
_myListener.receivedEvent.AddListener(OnMyEvent);

// OnDestroy()
_myListener?.receivedEvent.RemoveListener(OnMyEvent);
```

- Call `AddListener` after the channel is constructed, never in the constructor.
- Use the null-conditional `?.` in `OnDestroy` — `MQTTClient.Instance` may have torn down before the zone's own
  destructor runs (common in scene transitions).
- Typed channels (`MQTTChannel<T>`) must have a `T` decorated with plain public fields (no auto-properties),
  because `JsonUtility` requires them.

## Adding a new topic

Follow this checklist before introducing a new MQTT topic:

```text
- [ ] Topic name ends with `/`
- [ ] If paired with a "Trigger" topic, both are named `<Name>Trigger/` and `<Name>/`
- [ ] Owning script is identified — a topic must not be split across unrelated MonoBehaviours
- [ ] Channel direction (listener vs publisher) matches the intent
- [ ] `Start()` constructs the channel and registers listeners
- [ ] `OnDestroy()` removes listeners with null-conditional access
- [ ] Payload class (if typed) uses public fields — JsonUtility does not support properties
- [ ] sollertia-experiment is aware of the topic on its side — coordinate the change across both repos
- [ ] This skill's topic catalog is updated with the new entry
```

## Diagnosing a missed message

When a topic appears to work on one side but not the other, the probable causes cluster by symptom:

| Symptom                                                 | Likely cause                                                   | First check                                     |
|---------------------------------------------------------|----------------------------------------------------------------|-------------------------------------------------|
| Unity subscribes but never receives                     | Trailing slash dropped, or experiment publishes wrong topic    | Compare literal strings on both sides           |
| Unity publishes but experiment never receives           | `MQTTClient.Instance` not initialized before `Start()`         | Check Gimbl MainWindow is open / MQTT broker up |
| Typed message received but fields are all default       | Payload class used properties instead of public fields         | Grep the payload class for `{ get; set; }`      |
| Listener stops firing after scene change                | `OnDestroy()` removed the listener, `Start()` of the new scene did not re-register | Check scene wiring                    |
| Random loss under high rate                             | QoS level mismatch (default QoS is 2 on both sides)            | Inspect the broker's retained messages          |
| Unity receives its own `Gimbl/Stimulus/` publication    | Expected — `LickStimulusSpawner` subscribes to the same topic  | Not a bug                                       |

## Interaction contract

- **Never** hardcode a topic string in a skill or comment without cross-referencing the catalog in this file. Topic
  renames require updates on both sides of the contract.
- **Never** rely on message ordering between two different topics — MQTT provides per-topic ordering only.
- **Never** add a publisher and a subscriber on the same topic inside Unity expecting deduplication. MQTTnet delivers
  the message to every subscriber, including the local one, which is the intended behavior for `Gimbl/Stimulus/`.
